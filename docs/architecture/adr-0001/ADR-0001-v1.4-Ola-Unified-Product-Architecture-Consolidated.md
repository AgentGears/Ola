# ADR-0001: Consolidate Ola and Ouroboros into a Unified Governed Agent Continuity Product

- **Status:** Accepted — Frozen target-state architecture
- **Implementation readiness:** Pending closure of M0 and M1, including ratification of ADR-0001-A through ADR-0001-F and ADR-0001-R
- **Decision date:** 2026-07-22
- **Effective date:** 2026-07-22
- **Decision scope:** Product architecture, subsystem authority, convergence sequence, and change control
- **Product:** Ola
- **Supersedes:** Any architecture in which Ola and Ouroboros remain permanent peer products with separate public roadmaps, installations, release trains, and MCP surfaces
- **Current programme status:** Ouroboros 0.22A complete; Ola R2 remains the sole M0 blocker
- **Current execution constraint:** Close M0 and M1 before convergence runtime implementation

## 1. Context

Ola and Ouroboros were developed as separate projects with complementary but increasingly overlapping responsibilities.

Ola began as a local-first memory, evidence, retrieval, context-offload, and rehydration system. Its revised vision expands it into a governed cognitive-state and continuity platform founded on:

- append-only canonical history;
- evidence and provenance;
- epistemic state transitions;
- bitemporal validity;
- atomic memory transactions;
- auditability and rollback;
- rebuildable projections rather than graph-as-ground-truth;
- context compilation and rehydration.

Ouroboros is a reasoning-artifact and verification system for agents. It structures investigations using:

- objectives;
- observations;
- hypotheses and alternatives;
- verification plans and contracts;
- actions and execution results;
- support, contradiction, and inconclusive evidence relationships;
- branch history;
- conclusion qualification;
- skill replay and transfer evaluation;
- trace and study qualification.

The Memory Subagent specification adds a third major capability: a twelve-role executive control plane that plans retrieval, context, verification, memory maintenance, utility evaluation, rehydration, self-state, and policy execution.

Keeping Ola and Ouroboros as permanent peer products would require continuous compatibility management across identity, event ingestion, evidence references, task state, session lifecycle, retrieval, reasoning, rehydration, adapters, MCP tools, migrations, telemetry, release schedules, and efficacy studies.

Conversely, immediately collapsing both projects into one implementation, one database, or one undifferentiated state model would combine distinct integrity, retention, security, migration, and qualification concerns before equivalence has been demonstrated.

A product-level decision is therefore required.

## 2. Decision drivers

The decision is driven by the following requirements:

1. **One coherent end-user product.** Users should install, configure, and operate one system.
2. **Clear sovereign authority.** Canonical memory, evidence, investigation state, planning, and host actions must not have ambiguous ownership.
3. **Governed cognition.** Durable claims must be evidence-backed, policy-compliant, auditable, temporally explicit, and transactionally committed.
4. **Reasoning traceability.** Conclusions must remain traceable to explicit hypotheses, verification plans, actions, results, and evidence semantics.
5. **Incremental convergence.** Current safety and efficacy qualification must not be invalidated by premature integration.
6. **Preservation of bounded contexts.** Evidence storage and reasoning state have materially different integrity, retention, and mutation semantics.
7. **Operational simplicity.** One roadmap, repository, release train, installation path, and MCP surface should replace permanent cross-product coordination.
8. **Research validity.** Existing qualified ingestion and telemetry paths must remain attributable until replacement paths are independently qualified.
9. **Rebuildability.** Knowledge graphs and other read models must be disposable projections over canonical history.
10. **Measured consolidation.** Redundant implementations may be removed only after correctness and efficacy evidence supports removal.

## 3. Decision

Ola will become the single public product.

The product will contain four bounded internal components:

1. **Ola Core** — canonical cognitive-state, evidence, governance, retrieval, temporal history, policy, and continuity authority.
2. **Ouroboros Reasoning Engine** — investigation, verification, evidence interpretation, conclusion qualification, and skill-evaluation subsystem.
3. **Memory Subagent** — twelve-role cognitive control plane that plans and coordinates memory work across Ola Core and Ouroboros.
4. **Shared Runtime** — host adapters, identity, normalized event routing, lifecycle orchestration, orientation compilation, and the unified MCP surface.

The target operating model is:

```text
One product:       Ola
One roadmap:       Yes
One installation:  Yes
One repository:    Yes, after current gates
One release train: Yes
One public MCP:    Yes

One database:      No, not initially
One state model:   No, not initially
One runtime:       No, not necessarily
One ingestion path: Eventually, after shadow qualification
```

The canonical separation of powers is:

> **The host agent acts. The Memory Subagent plans. Ouroboros investigates and verifies. Ola validates and commits.**

## 5. Authority model

### 5.1 Separation of powers

| Power | Component | Authority |
|---|---|---|
| Acting | Host agent | Reads, executes, edits, communicates, and performs external actions |
| Planning | Memory Subagent | Determines what cognitive and memory work should happen |
| Investigating | Ouroboros | Determines what an investigation's evidence supports, contradicts, or leaves unresolved |
| Governing | Ola Core | Determines what may become canonical durable cognitive state |

No component may silently assume another component's authority.

- A recalled item is not true merely because retrieval returned it.
- An Ouroboros conclusion is not automatically an Ola verified claim.
- A Memory Subagent proposal is not automatically a committed memory.
- A successful command is not automatically proof of a hypothesis.
- A supported hypothesis is not automatically a completed investigation.
- A completed investigation is not automatically a canonical durable claim.

### 5.2 Canonical ownership

| Domain | Canonical owner |
|---|---|
| Raw tool output and byte-level evidence | Ola Core |
| Evidence digests, locators, sensitivity, and retention | Ola Core |
| Durable observations | Ola Core |
| Canonical claims and epistemic states | Ola Core |
| Valid time and system time | Ola Core |
| Policy definitions and versions | Ola Core |
| Memory transactions, audit, and rollback | Ola Core |
| Cross-investigation entity lineage | Ola Core |
| Rebuildable knowledge and retrieval projections | Ola Core |
| Active investigation objective | Ouroboros |
| Hypotheses, assumptions, and alternatives | Ouroboros |
| Verification contracts | Ouroboros |
| Action-result correlation | Ouroboros |
| Evidence-support and contradiction interpretation | Ouroboros |
| Investigation branch history | Ouroboros |
| Investigation conclusion qualification | Ouroboros |
| Skill replay and transfer evidence | Ouroboros |

Internal persistence domains remain separate until consolidation demonstrates a correctness, security, operational, or measurable efficacy benefit.

## 6. Memory Subagent decision

The Memory Subagent retains the following twelve roles as its canonical specification:

| # | Role | Responsibility |
|---:|---|---|
| 1 | Retrieval planner | Chooses memory types, scope, and retrieval strategy |
| 2 | Context curator | Selects information for working context under a bounded budget |
| 3 | Memory gap detector | Produces concrete missing-knowledge statements |
| 4 | Verification coordinator | Chooses claims requiring verification and appropriate methods |
| 5 | Memory write proposer | Proposes observations, claims, decisions, failed approaches, and outcomes |
| 6 | Consolidation planner | Compresses fragmented memory without losing evidence or lineage |
| 7 | Revision and contradiction manager | Classifies conflicts and proposes governed resolution |
| 8 | Staleness monitor | Detects dependency and environmental changes requiring revalidation |
| 9 | Outcome and utility recorder | Records practical usefulness independently of truth status |
| 10 | Rehydration planner | Selects the minimum durable state required for resumption |
| 11 | Self-state maintainer | Maintains measurable operational state and uncertainty |
| 12 | Memory policy executor | Applies policy during planning and proposal construction without replacing Ola Core’s authoritative evaluation and enforcement |

These roles form a closed cognitive-control loop:

```text
Sense
  retrieval · gaps · staleness · self-state

Assess
  context curation · contradiction · policy

Plan
  verification · consolidation · revision

Propose
  writes · utility updates · rehydration

Learn
  evaluate outcomes and improve future planning
```

The Memory Subagent is proposal-only with respect to canonical state. Its decisions, exclusions, plans, and policy applications must be inspectable and eligible for audit.

## 7. Architectural invariants

The following invariants are mandatory.

### 7.1 Canonical event history

The append-only Ola event history is the canonical source of durable cognitive state.

Materialized views may be deleted and rebuilt without loss of canonical information.

### 7.2 Graphs are projections

The Ola knowledge graph is a rebuildable projection, not canonical ground truth.

Ouroboros may maintain an operational investigation graph, but any information that must survive as canonical cross-investigation history must be anchored into Ola through versioned events and governed transactions.

### 7.3 Evidence before promotion

A claim cannot become verified merely because an agent, subagent, graph extractor, model, summary, or recalled memory asserts it.

Promotion requires:

- valid provenance;
- existing evidence;
- an allowed state transition;
- a policy-compliant verification method;
- an atomic transaction;
- and an audit event.

### 7.4 Proposal versus commitment

Memory Subagent and Ouroboros outputs remain proposals or investigative artifacts until Ola accepts them.

```text
proposal
→ governance validation
→ accepted | rejected | needs_evidence |
  conflict_detected | policy_review_required
```

### 7.5 Truth and utility remain separate

Durable items may carry both an epistemic state and a utility state.

```text
epistemic:
  observed | inferred | candidate | verified |
  contested | possibly_stale | stale | superseded

utility:
  useful | partially_useful | irrelevant |
  dead_end | misleading | harmful
```

Utility must not silently promote truth.

### 7.6 Bitemporal semantics

Durable claims distinguish:

- **valid time** — when the claim was true in the represented world;
- **system time** — when Ola learned or recorded it.

### 7.7 Conservative trust propagation

Untrusted external content, third-party claims, recalled summaries, and agent-generated inferences do not gain authority through repetition, summarization, or transformation.

### 7.8 No direct cross-store mutation

Components communicate through versioned contracts and stable references.

- Ouroboros must not write directly into Ola's internal storage.
- Ola must not mutate Ouroboros investigation structures through undocumented storage access.
- The Memory Subagent must not bypass either subsystem's validation boundary.

### 7.9 Idempotent ingestion

Every retained cross-component artifact has stable identity and idempotent ingestion semantics.

### 7.10 Explainability

The product must be able to answer:

- Why is this remembered?
- What evidence supports it?
- When was it last verified?
- What contradicts it?
- Why was it included in context?
- Which policy permitted the transition?
- What changes if it is corrected, superseded, or deleted?

### 7.11 One public product

Users are not required to install, configure, or coordinate Ola and Ouroboros as separate products.

## 8. Contract family

Runtime integration must use versioned contracts.

### 8.1 Identity hierarchy

The authoritative cross-component identity hierarchy and envelope requirements are defined by ADR-0001-D.

Generic `session_id` must not replace role-qualified orchestrator, child, attempt, context, invocation, stream, or sequence identities.

The minimum qualified hierarchy includes:

```text

project_id
task_id
run_id
attempt_id
context_id
orchestrator_session_id
child_session_id
session_id
invocation_id
investigation_id
stream_id
sequence_scope
source_sequence
event_id
observation_id
evidence_ref_id
claim_id
entity_id
procedure_id
policy_version
```

### 8.2 Normalized host event

A normalized host event contains:

- stable event identity;
- qualified workspace/project/task/run/attempt/context/session/invocation binding as applicable;
- producer and version;
- event type;
- timestamp;
- payload digest;
- source class and source trust;
- evidence assurance where applicable;
- confidentiality class and data categories;
- secret-detection disposition;
- retention mode, retention scope, expiration, and hold status;
- access scope;
- optional raw-evidence reference.

### 8.3 Ola evidence reference

An evidence reference contains:

- provider;
- observation identity;
- exact content digest and digest algorithm;
- stream or artifact class;
- bounded byte or record locator;
- source class and source trust;
- evidence assurance;
- confidentiality class and data categories;
- secret-detection disposition;
- retention mode, retention scope, expiration, and hold status;
- access scope.

### 8.4 Ouroboros reasoning fragment

A reasoning fragment contains:

- active objective;
- hypotheses;
- assumptions;
- rejected alternatives;
- pending verifications;
- evidence relationships;
- current conclusion status;
- next justified action.

### 8.5 Memory transaction proposal

A proposal contains:

- requested operation;
- target identity;
- provenance;
- requested epistemic transition;
- temporal fields;
- policy version;
- supporting evidence;
- expected conflict behavior.

### 8.6 Governance receipt

Ola returns exactly one durable disposition:

```text
accepted
rejected
needs_evidence
conflict_detected
policy_review_required
```

### 8.7 Combined orientation packet

The unified packet must visibly distinguish:

```text
verified finding
observation
remembered claim
unverified summary
active hypothesis
rejected alternative
stale or unsafe item
pending verification
```

## 9. Runtime flow

The authoritative runtime flow is defined by ADR-0001-C:

```text
1. Memory Subagent proposes a verification objective.
2. Ouroboros creates the verification contract and expected interpretations.
3. Shared Runtime routes an action request.
4. Host agent or an explicitly authorized execution adapter performs the action.
5. Ola admits the raw result as evidence and records provenance.
6. Ouroboros correlates and interprets the result.
7. Memory Subagent proposes memory consequences.
8. Ola governance validates and commits any durable transition.
9. Ola emits canonical events through its durable delivery path.
10. Projections and orientation consumers converge idempotently.
11. Shared Runtime assembles and delivers bounded context without changing epistemic labels.
```

Ouroboros may coordinate verification but does not acquire external-action authority. Failure at one stage does not imply success at a later stage.

### M8 — Build one orientation and rehydration compiler

Inputs:

```text

  verified claims
  observations
  evidence
  history
  procedures
  freshness and policy state
```

The compiler may assemble, rank, truncate, format, and deliver, but may not:

- promote a remembered claim to verified;

- merge contradictory items without preserving the conflict;
- hide uncertainty because of context-budget pressure;
- change source-trust, evidence-assurance, freshness, confidentiality, data-category, secret-disposition, retention, safety, or epistemic labels.

Every omission must be attributable to a Memory Subagent selection or an explicit budget rule.

**Gate:** paired interruption experiments demonstrate successful recovery, less duplicated work, correct evidence attribution, no increase in stale-claim use, and no loss of final verification quality.

## 11. End-user experience

The user installs Ola once and continues using a preferred host agent.

The intended flow is:

```text
agent acts
→ evidence is captured
→ investigation state is structured
→ memory changes are governed
→ useful context is recalled
→ interrupted work can resume
```

The product must support questions such as:

- What are we working on?
- What has already been verified?
- What remains uncertain?
- Why do you believe this?
- What evidence supports it?
- What changed since the previous session?
- Which path already failed?
- What is the next justified action?
- Why was this memory included?
- What will happen if I correct or delete it?

The user should not need to know which internal subsystem produced the answer.

## Transitional authority rule

Target-state ownership does not transfer operational authority before the corresponding milestone gate closes. Existing qualified stores and runtime paths remain authoritative until a recorded cutover decision establishes:

```text
old authority
new authority
shadow period
equivalence evidence
cutover event
rollback owner
rollback procedure
post-cutover retention
```

The detailed protocol is governed by ADR-0001-B.

## 13. Consequences

### 13.1 Positive consequences

- One product replaces a permanent compatibility program.
- Product-level priorities and releases become coherent.
- User-facing duplication is eliminated incrementally.
- Authority boundaries become explicit and testable.
- Ola's evidence and governance model prevents reasoning artifacts from becoming canonical without validation.
- Ouroboros retains its stronger investigation and verification semantics.
- The Memory Subagent gains a clear proposal-only control-plane role.
- A monorepo allows cross-component contract changes and tests to land atomically.
- Existing qualification paths remain protected during convergence.
- Internal persistence can evolve independently until evidence supports consolidation.
- Combined orientation and rehydration become possible without collapsing all state into one schema.
- Efficacy can be measured through controlled ablations inside one product.

### 13.2 Negative consequences and costs

- The product becomes architecturally more complex before it becomes operationally simpler.
- A polyglot monorepo requires root orchestration, pinned runtime floors, and separate component builds.
- Shared releases increase blast radius.
- Event sourcing, governance validation, and multi-dimensional retrieval may add latency.
- Projection rebuilds and schema evolution require explicit operational tooling.
- Shadow ingestion and qualification extend the transition period.
- Separate internal stores require durable cross-component references and migration discipline.
- The Memory Subagent requires role-level evaluation, not merely end-to-end task tests.
- A single product roadmap must manage engineering, runtime, migration, governance, and research priorities together.

## 15. Alternatives considered

### Alternative A — Keep Ola and Ouroboros as permanent peer products

**Rejected.**

This would require permanent compatibility management across identities, events, task state, sessions, evidence, retrieval, rehydration, MCP tools, adapters, migrations, telemetry, releases, and studies. Overlapping concepts would continue attracting duplicate implementations and ambiguous ownership.

### Alternative B — Immediate deep merge into one database and state model

**Rejected.**

The evidence and reasoning domains have different mutation, retention, security, corruption, and qualification semantics. An immediate deep merge would increase migration risk, obscure failure attribution, and invalidate qualified paths before equivalence is demonstrated.

### Alternative C — One Ola product with bounded internal subsystems

**Accepted.**

This removes the product-level coordination tax while preserving bounded contexts and enabling incremental, evidence-driven convergence.

### Alternative D — Use Ouroboros as the public product name

**Rejected.**

Ola already owns the broader memory, evidence, adapter, installation, migration, and continuity proposition. Renaming around Ouroboros would redirect established work without architectural benefit.

### Alternative E — Introduce a new umbrella product name

**Rejected.**

A new name would add another migration, documentation burden, namespace transition, and user-education problem without solving an architectural requirement.

### Alternative F — Build a permanent protocol-only federation

**Rejected as the final state; permitted only as a transition mechanism.**

Versioned protocols and stable references are required internally, but they serve convergence and bounded contexts inside one product rather than preserving two permanent peer products.

## 16. Non-goals

The initial convergence does not include:

- one shared database;
- one undifferentiated state model;
- rewriting Ouroboros in Node.js;
- rewriting Ola in Python;

# ADR-0001-B: Transitional Authority and Cutover Protocol

- **Parent decision:** ADR-0001
- **Status:** Proposed — frozen candidate for ratification
- **Decision scope:** Operational authority before, during, and after subsystem convergence
- **Prepared:** 2026-07-22

## 1. Context

ADR-0001 defines target-state ownership:

- Ola Core owns canonical cognitive state and evidence.
- Ouroboros owns investigation and verification semantics.
- Shared Runtime owns lifecycle, identity, orientation assembly, and public MCP routing.
- The Memory Subagent plans but does not commit.

Some target capabilities do not yet exist or are not yet qualified. Therefore target-state ownership cannot be interpreted as immediate operational authority.

A controlled transition requires explicit authority phases and durable cutover decisions.

## 2. Decision

The following rule is frozen:

> **Target-state ownership does not transfer operational authority before the corresponding milestone gate closes. Existing qualified stores and runtime paths remain authoritative until a recorded cutover decision establishes the replacement authority, equivalence evidence, rollback procedure, and post-cutover retention policy.**

Every authority domain transitions through four phases:

```text
current authority
→ shadow authority
→ cutover authority
→ post-cutover authority
```

## 3. Authority phases

### 3.1 Current authority

The existing qualified component remains authoritative for production behavior.

Properties:

- all writes and reads continue through the existing path;
- the candidate replacement may be absent or disabled;
- no target-state ownership claim overrides current behavior;
- qualification remains attributable to the current implementation.

### 3.2 Shadow authority

The candidate path receives equivalent inputs or reads replicated artifacts but cannot independently determine production state.

Properties:

- current authority remains the source of operational truth;
- candidate output is compared but not committed as canonical;
- mismatches are recorded;
- candidate failures do not alter current authority;
- data capture must obey minimum privacy and retention controls;
- shadow output is explicitly labeled non-authoritative.

### 3.3 Cutover authority

A durable cutover decision transfers operational authority to the candidate path.

Properties:

- equivalence criteria have passed;
- cutover preconditions are freshly verified;
- the cutover event is atomic within the controlling store;
- rollback ownership and procedure are active;
- unsupported mixed-authority states are refused;
- old authority becomes read-only, retained, or archived according to policy.

### 3.4 Post-cutover authority

The new path is authoritative.

Properties:

- all supported production writes route through the new authority;
- the old path cannot silently resume writes;
- ongoing drift checks remain active for a defined stabilization period;
- rollback remains available until the retention window closes;
- removal of the old path requires a separate evidence-backed decision.

## 4. Cutover record

Every cutover must produce an immutable record containing:

```text
cutover_id
authority_domain
old_authority
new_authority
shadow_start
shadow_end
input_scope
equivalence_criteria
equivalence_evidence
known_exceptions
cutover_preconditions
cutover_event
cutover_timestamp
rollback_owner
rollback_procedure
rollback_deadline
post_cutover_retention
stabilization_checks
approvers
record_digest
```

Examples of authority domains include:

```text
raw_evidence_ingestion
investigation_result_correlation
canonical_claim_commit
orientation_packet_delivery
public_mcp_routing
identity_assignment
projection_serving
```

One cutover record must not transfer unrelated domains implicitly.

## 5. Equivalence evidence

Equivalence criteria must be defined before the shadow period begins.

Depending on the domain, they may include:

- complete required-event coverage;
- matching or explainable event counts;
- correct task, run, session, and child-agent attribution;
- matching payload digests where comparable;
- ordering preservation;
- no cross-task leakage;
- equivalent refusal behavior;
- latency within an accepted bound;
- identical governance disposition;
- deterministic replay;
- no privacy or retention regression.

A candidate path is not equivalent merely because its happy-path output resembles the current path.

## 6. Cutover preconditions

Immediately before cutover, the controller must verify:

- current authority remains healthy;
- candidate authority remains healthy;
- identity mapping is unambiguous;
- contract versions are supported;
- pending messages are below the defined threshold or drained;
- dead-letter queues are reviewed;
- rollback artifacts are complete;
- privacy and retention controls are active;
- production-data backup or recovery controls are current;
- no conflicting cutover is active.

## 7. Rollback protocol

Every cutover must define whether rollback is:

```text
component-local
whole-product
manual-only
automatic-under-bounded-conditions
```

Rollback must specify:

- exact trigger conditions;
- authority to approve or initiate rollback;
- state that can be reversed;
- state that must be reconciled;
- message replay behavior;
- data written by the new authority;
- treatment of receipts and projections;
- how split-brain writes are prevented;
- post-rollback verification.

If a contract change is not backward-compatible, whole-product rollback is required unless a tested translation path exists.

## 8. Mixed-authority refusal

The system must fail closed when:

- both current and candidate paths can commit the same authority domain;
- authority metadata is missing or conflicting;
- cutover state cannot be determined;
- a candidate consumer processes unsupported schema versions;
- the old path resumes writes after cutover;
- replay would create duplicate canonical transitions;
- rollback cannot establish a single writer.

## 9. Store retention after cutover

The old store or path must receive one disposition:

```text
read_only_for_audit
retained_for_rollback
archived
migrated_and_verified
destroyed_after_retention
```

Deletion requires:

- completed retention window;
- verified replacement authority;
- preserved audit and provenance requirements;
- privacy and legal-policy compliance;
- explicit deletion authorization;
- evidence that rollback no longer depends on the old store.

## 10. Domain-specific transition rules

### 10.1 Evidence ingestion

Before Ola evidence admission becomes canonical:

```text
initial:
  existing qualified Ouroboros path = current authority
  candidate Ola path                = non-authoritative shadow

after recorded cutover:
  Ola path                           = post-cutover authority
  former Ouroboros path              = optional shadow auditor during stabilization
```

Additionally:

- minimum source, trust, assurance, confidentiality, data-category, secret, retention, scope, and access controls must exist;
- payload digests and qualified identities are compared;
- no conclusion promotion occurs solely from shadow evidence;
- cutover follows the domain-specific record and rollback protocol.

### 10.2 Identity routing

Shared Runtime identity becomes authoritative only after:

- project/task/run/session mapping is deterministic;
- child-agent attribution passes;
- historical identifiers remain resolvable;
- collision and replay tests pass.

### 10.3 Orientation delivery

Unified orientation becomes authoritative only after:

- semantic labels remain unchanged;
- provenance survives assembly;
- omission rationale is available;
- truncation behavior is deterministic;
- current resume paths remain recoverable.

### 10.4 Public MCP routing

The unified Ola namespace becomes authoritative only after:

- legacy commands delegate correctly;
- authorization and capability checks are equivalent;
- public error semantics are stable;
- rollback to legacy routing is tested.

## 11. Consequences

### Positive

- Prevents premature interpretation of target-state authority.
- Gives each migration a measurable and reversible cutover.
- Preserves qualification and attribution.
- Prevents split-brain writes.
- Makes retention and decommissioning explicit.

### Negative

- Requires shadow operation and comparison tooling.
- Extends the lifetime of duplicate paths.
- Adds durable cutover records and rollback maintenance.
- May require domain-by-domain rather than single-event convergence.

## 12. Acceptance criteria

This annex is accepted when:

- all authority domains have named current owners;
- the four-phase authority model is adopted;
- the cutover record schema is approved;
- evidence-ingestion, identity, orientation, and MCP cutovers have assigned owners;
- rollback classification rules are accepted;
- mixed-authority refusal tests are planned.

# ADR-0001-C: Runtime Authority and Distributed Failure Semantics

- **Parent decision:** ADR-0001
- **Status:** Proposed — frozen candidate for ratification
- **Decision scope:** Runtime action authority, cross-store delivery, intermediate states, retries, recovery, and convergence
- **Prepared:** 2026-07-22

## 1. Context

The unified product crosses multiple bounded components and potentially multiple processes, runtimes, and stores.

The architecture must preserve the frozen separation of powers:

```text
Host agent:       acts
Memory Subagent:  plans
Ouroboros:        investigates and interprets
Ola Core:         governs and commits
Shared Runtime:   routes and assembles
```

No distributed transaction can atomically commit every store and process. The system therefore requires durable eventual consistency with explicit intermediate states.

## 2. Decision

Cross-component work uses:

```text
local transaction
→ durable outbox event
→ versioned envelope
→ idempotent inbox consumer
→ local commit
→ durable receipt
→ retry, quarantine, or convergence
```

The system does not promise cross-store ACID transactions.

A component may coordinate an action, but only the host agent or an explicitly authorized execution adapter performs external actions.

## 3. Canonical runtime flow

```text
1. Memory Subagent proposes a verification objective.
2. Ouroboros creates a verification contract and expected interpretations.
3. Shared Runtime routes an action request.
4. Host agent or authorized execution adapter performs the action.
5. Ola admits the raw result as evidence.
6. Ouroboros correlates and interprets the result.
7. Memory Subagent proposes memory consequences.
8. Ola governs and commits any durable transition.
9. Ola emits canonical events through its outbox.
10. Projection and orientation consumers converge idempotently.
11. Shared Runtime delivers deterministic receipts and context.
```

Ouroboros may coordinate execution but does not become an undeclared external-action authority.

## 4. Durable messaging pattern

When a producer changes durable local state, that mutation and its outbound event must commit atomically in the same local transaction.

A stateless adapter or transport relay must durably enqueue the event before acknowledging successful receipt.

All producers must then:

1. publish or forward the durable event asynchronously;
2. retain or delegate retention until acknowledged under the protocol;
3. retry with the same idempotency identity;
4. quarantine permanently incompatible or malformed events;
5. expose delivery status.

Each consuming component must:

1. validate the envelope before mutation;
2. check inbox/idempotency state;
3. apply the local transition atomically;
4. store the processed event identity;
5. create a durable receipt;
6. make retries return the same result.

## 5. Required intermediate states

The product must represent intermediate states explicitly, including at least:

```text
evidence_admitted_investigation_pending
investigation_associated_interpretation_pending
proposal_received_governance_pending
transaction_committed_projection_pending
transaction_committed_receipt_pending
receipt_committed_delivery_pending
orientation_inputs_ready_assembly_pending
quarantined_contract_incompatible
quarantined_policy_unresolvable
manual_reconciliation_required
```

Intermediate states are inspectable operational facts, not hidden implementation details.

## 6. Failure semantics

### 6.1 Evidence admitted, investigation association fails

State:

```text
evidence_admitted_investigation_pending
```

Required behavior:

- preserve admitted evidence;
- retry association idempotently;
- do not discard or duplicate evidence;
- do not infer an evidence-to-hypothesis relationship;
- escalate after bounded retries.

### 6.2 Investigation interpretation succeeds, proposal delivery fails

Required behavior:

- preserve Ouroboros interpretation;
- keep the proposal in the outbox;
- retry with the same idempotency key;
- prevent a second proposal identity;
- surface pending governance status.

### 6.3 Ola commits a transaction, projection update fails

State:

```text
transaction_committed_projection_pending
```

Required behavior:

- canonical state remains committed;
- projection must not be treated as authoritative;
- projection worker retries from canonical events;
- reads requiring freshness either use canonical fallback or declare projection lag;
- no compensating rollback occurs solely because a projection is delayed.

### 6.4 Governance commits, receipt delivery fails

State:

```text
receipt_committed_delivery_pending
```

Required behavior:

- replay returns the same durable receipt;
- the sender does not create a second transition;
- receipt delivery retries independently;
- operator status distinguishes committed from delivered.

### 6.5 Unsupported contract version

State:

```text
quarantined_contract_incompatible
```

Required behavior:

- no consumer mutation;
- original bytes retained under retention policy;
- bounded diagnostic recorded;
- operator-visible remediation path;
- no silent coercion to a different schema.

## 7. Idempotency

Every side-effecting request requires:

```text
idempotency_key
event_id
producer_id
operation
target_identity
payload_digest
```

The receiver must enforce:

- identical replay returns the original durable result;
- same idempotency key with different payload refuses;
- duplicate delivery cannot create duplicate canonical events;
- receipt identity remains stable;
- retries do not change timestamps that are part of semantic identity.

## 8. Ordering

Ordering guarantees are scoped, not global.

The contract family must define ordering per stream, such as:

```text
project/task/run/session stream
investigation stream
claim stream
policy stream
projection stream
```

Consumers must not assume ordering across unrelated streams.

When a gap is detected:

- stop applying dependent events;
- request replay or wait for the missing sequence;
- avoid speculative reordering;
- quarantine irreconcilable sequence conflicts.

## 9. Retry policy

Retry behavior must specify:

- maximum attempts or elapsed time;
- exponential backoff and jitter;
- retryable versus terminal errors;
- circuit-breaker behavior;
- operator escalation;
- dead-letter/quarantine disposition;
- whether retry preserves original event time.

Retries must not mask policy refusal or schema incompatibility as transient failure.

## 10. Projection consistency

Projections are eventually consistent and disposable.

Every projection response must be able to expose:

```text
projection_version
source_event_position
built_at
lag_status
freshness_class
```

When projection lag exceeds policy:

- retrieval may fall back to canonical reads where supported;
- orientation must label stale projection content;
- high-assurance operations must refuse or wait;
- no projection may promote its own content to canonical state.

## 11. Reconciliation

Manual reconciliation is required when:

- two different payloads claim one idempotency key;
- both sides independently committed incompatible transitions;
- event sequence cannot be repaired;
- cutover metadata is conflicting;
- rollback cannot establish a single writer;
- retained evidence no longer matches its digest;
- policy version required for evaluation is unavailable.

Reconciliation must create an auditable decision record.

## 12. Observability

Operational status must expose:

- outbox depth;
- inbox lag;
- oldest pending event age;
- retry counts;
- quarantined-event counts;
- projection lag;
- pending governance receipts;
- unresolved reconciliation cases;
- active cutover phase.

Diagnostics must remain bounded and avoid leaking sensitive payloads.

## 13. Operational-artifact authority

| Artifact | Canonical owner |
|---|---|
| Cutover state and routing authority | Shared Runtime operational control store |
| Cutover audit copy | Ola Core audit event class |
| Memory Subagent cycle and planning artifact | Ola Core operational/audit event class, admitted through contract |
| Investigation execution state | Ouroboros |
| Governance receipt | Ola Core |
| Outbox/inbox delivery state | Owning producer or consumer component |
| Cross-component reconciliation decision | Shared Runtime product-operations authority, with durable Ola audit copy |
| Projection freshness and lag state | Projection owner, referenced from Ola status |
| Contract quarantine record | Receiving component protected quarantine store |

Ownership of an operational record does not transfer cognitive-state sovereignty.

## 14. Consequences

### Positive

- Makes distributed failure recoverable and inspectable.
- Preserves canonical commits when projections or delivery fail.
- Prevents duplicate transitions.
- Keeps action authority with the host.
- Avoids unrealistic cross-store atomicity claims.

### Negative

- Introduces outbox/inbox infrastructure.
- Requires intermediate-state handling in APIs and UX.
- Adds retry, quarantine, and reconciliation operations.
- May expose temporary inconsistency to clients.

## 15. Acceptance criteria

This annex is accepted when:

- the corrected runtime flow is adopted;
- outbox/inbox is the default cross-component pattern;
- required intermediate states are part of the status model;
- idempotency and ordering rules are accepted;
- projection-lag behavior is defined;
- failure-injection tests are assigned to M3–M8.

1. a strict schema;

### 2.2 Canonical serialization

```text
digest_algorithm: sha256
```

JSON envelopes use RFC 8785 JSON Canonicalization Scheme semantics. Binary evidence uses SHA-256 over exact bytes and is referenced rather than embedded.

Contracts additionally define:

- timestamp precision and UTC normalization;
- null-versus-absent semantics;
- digest coverage;
- treatment of unknown fields;
- maximum payload size;
- binary-content reference rules.

Digests must be computed over canonical bytes. A future canonicalization change requires a new `canonicalization_version` and compatibility rules.

## 3. Identity semantics

### 3.1 Event identity

`event_id` identifies one immutable emitted event.

### 3.2 Idempotency identity

`idempotency_key` identifies one intended side effect.

The same idempotency key:

- with the same canonical payload returns the same result;
- with different canonical payload refuses as a conflict.

### 3.3 Correlation

`correlation_id` groups a logical workflow.

### 3.4 Causation

`causation_id` identifies the event or request that directly caused the current event.

### 3.5 Parent relation

`parent_event_id` identifies a structural parent where the contract requires one.

These identities must not be overloaded.

## 4. Time semantics

Contracts distinguish:

```text
occurred_at:
  when the represented action or observation occurred

recorded_at:
  when the producing system durably recorded it

valid_from / valid_to:
  the represented world's validity interval
```

Clock uncertainty or source-clock quality must be representable when relevant.

Retries do not alter `occurred_at`. A replay may have a later delivery time without becoming a new semantic event.

## 5. Duplicate handling

Consumers must implement:

- event-ID deduplication;
- idempotency-key enforcement;
- payload-digest comparison;
- durable duplicate receipts;
- no second side effect on replay.

A duplicate with matching identity and digest is not an error.

A duplicate identity with different digest is a terminal conflict.

## 6. Ordering guarantees

Every contract declares one ordering mode:

```text
unordered
ordered_within_stream
strictly_sequenced_within_stream
```

For sequenced streams, `stream_id` and `sequence_scope` are mandatory. The contract specifies:

- stream identity;
- sequence origin;
- gap behavior;
- replay behavior;
- duplicate sequence handling;
- conflict behavior.

No consumer may infer global ordering from timestamps alone.

## 7. Versioning

### 7.1 Schema versioning

Schema versions use explicit major/minor semantics:

```text
major:
  incompatible interpretation or required-field change

minor:
  backward-compatible optional extension
```

Persisted artifact schemas may use integer versions if the compatibility rule is equivalent and documented.

### 7.2 Producer and consumer support

The root compatibility manifest records supported ranges.

A consumer must:

- accept supported versions;
- preserve unknown optional fields only when the contract permits;
- refuse unsupported major versions;
- never silently reinterpret an incompatible payload.

### 7.3 Negotiation

Interactive transports may negotiate a common version before exchange.

Asynchronous transports rely on the compatibility manifest and quarantine unsupported versions.

## 8. Unknown-field behavior

Each schema declares one policy:

```text
reject_unknown
preserve_unknown
ignore_unknown_for_processing_but_preserve_bytes
```

Security-, governance-, evidence-, and transaction-critical schemas default to `reject_unknown`.

Orientation and forward-compatible display fragments may use a more permissive policy only when canonical semantics are unaffected.

## 9. Replay behavior

Every event contract defines:

- whether replay is allowed;
- whether replay re-emits the original event ID;
- whether derived receipts are reused;
- how sequence positions are restored;
- how expired retention affects replay;
- whether replay may rebuild projections but not canonical events.

Canonical event replay must not append duplicate canonical history.

## 10. Retry and timeout semantics

Requests define:

```text
request_timeout
processing_deadline
retryable_errors
terminal_errors
maximum_retry_window
receipt_query_method
```

A client timeout does not imply server failure.

After a timeout, the client queries by idempotency key or retries with the same key.

## 11. Partial failure

Contracts must distinguish:

```text
not_received
received_not_committed
committed_receipt_pending
committed_and_delivered
rejected
quarantined
manual_reconciliation_required
```

“Unknown” responses must direct the caller to a deterministic status query.

## 12. Governance receipts

A governance receipt is immutable and idempotent.

Required fields include:

```text
receipt_id
proposal_id
idempotency_key
disposition
governance_policy_version
canonical_event_ids
conflict_references
required_evidence
recorded_at
receipt_digest
```

Allowed dispositions:

```text
accepted
rejected
needs_evidence
conflict_detected
policy_review_required
```

Replaying the same proposal returns the same receipt.

## 13. Dead-letter and quarantine behavior

Malformed, unsupported, or irreconcilable messages are quarantined with:

```text
quarantine_id
original_event_id
reason_code
schema_name
schema_version
producer_id
payload_digest
first_seen
last_attempt
attempt_count
operator_action_required
```

Raw sensitive payloads remain in the protected evidence domain and are not copied into general diagnostics.

## 14. Compatibility manifest

One public Ola release contains independently versioned internal components.

The root manifest records:

```text
ola_product_version
ola_core_version
ouroboros_engine_version
memory_subagent_version
shared_runtime_version
contract_family_version
projection_versions
minimum_data_schema_versions
supported_contract_ranges
supported_projection_ranges
migration_requirements
```

The supported-version matrix is atomic for each public release.

## 15. Release and rollback semantics

- Component-local rollback is allowed only when contracts remain compatible.
- Whole-product rollback is required for incompatible contract changes unless a tested translation layer exists.
- A release must not advertise a component combination outside the compatibility manifest.
- Persisted artifacts must identify the contract and component versions that created them.

## 16. Security and privacy fields

Before M5, evidence-related envelopes must carry:

- source class;
- source trust;
- evidence assurance;
- confidentiality class;
- data categories;
- secret-detection disposition;
- retention mode;
- retention scope;
- expiration and hold status;
- workspace/user access scope;
- redaction outcome.

Missing mandatory classification causes refusal or protected quarantine.

## 17. Consequences

### Positive

- Makes cross-language and long-lived contracts deterministic.
- Prevents replay and retry from creating duplicate transitions.
- Makes compatibility and release composition explicit.
- Supports durable receipts and status queries.
- Reduces silent schema drift.

### Negative

- Increases envelope size and validation cost.
- Requires canonical serialization libraries in each runtime.
- Requires compatibility and migration tooling.
- Makes casual ad hoc message exchange non-compliant.

## 18. Acceptance criteria

This annex is accepted when:

- the base envelope is approved;
- canonical serialization is selected or specified for M3;
- identity and time semantics are accepted;
- duplicate, replay, timeout, and partial-failure behavior is frozen;
- the compatibility-manifest fields are adopted;
- governance receipts are defined as immutable and idempotent.

# ADR-0001-E: Memory Subagent Control-Cycle Protocol

- **Parent decision:** ADR-0001
- **Status:** Proposed — frozen candidate for ratification
- **Decision scope:** Executable protocol for the twelve Memory Subagent roles
- **Prepared:** 2026-07-22

## 1. Context

ADR-0001 freezes twelve Memory Subagent roles, but a list of roles does not by itself define an executable cognitive control plane.

The product requires:

- a canonical cycle;
- structured inputs and outputs;
- role sequencing;
- budgets;
- stopping and escalation rules;
- auditable decisions;
- utility feedback that cannot override epistemic governance.

## 2. Decision

The Memory Subagent operates through a versioned control cycle:

```text
observe
→ retrieve
→ identify gaps and risks
→ curate context
→ rank candidate cognitive actions
→ select and propose an action
→ await execution or governance outcome
→ attribute utility
→ update operational self-state
→ continue, stop, or escalate
```

The cycle may skip stages only when the cycle record states why they are inapplicable.

## 3. Cycle record

Every cycle has a durable inspectable record:

```text
cycle_id
schema_version
project_id
task_id
run_id
session_id
trigger
goal
input_snapshot_ref
policy_version
autonomy_tier
budget
candidate_actions
selected_action
selection_rationale
expected_information_gain
expected_cost
expected_risk
required_approval
execution_or_governance_refs
result
utility_attribution
self_state_delta
stopping_decision
created_at
completed_at
cycle_digest
```

The cycle record is an operational planning artifact. It is not automatically canonical knowledge.

## 4. Cycle stages

### 4.1 Observe

Inputs:

- current user or task objective;
- host state;
- latest canonical Ola status;
- active Ouroboros investigation state;
- previous cycle outcome;
- policy and budget.

Outputs:

- bounded state snapshot;
- detected trigger;
- initial risk and uncertainty classification.

### 4.2 Retrieve

Role owners:

- Retrieval planner;
- Ola retrieval services.

The Subagent chooses retrieval modes such as:

```text
lexical
entity_scoped
graph_scoped
episodic
recent
historical
evidence_heavy
procedure_scoped
policy_scoped
```

The retrieval plan records expected value, cost, and scope.

### 4.3 Identify gaps and risks

Role owners:

- Memory gap detector;
- Staleness monitor;
- Revision and contradiction manager.

Outputs include concrete statements:

```text
No verified claim explains behavior X.
Source Y changed after claim C was verified.
Two current claims conflict in the same scope.
Required evidence is unavailable.
Retrieved information is stale or unsafe.
```

### 4.4 Curate context

Role owner:

- Context curator.

The curator classifies items:

```text
essential_now
possibly_relevant
background_only
unsafe_or_stale
excluded_by_budget
```

Every exclusion has a reason code.

The curator may reduce content but must preserve:

- provenance;
- epistemic labels;
- conflict labels;
- freshness;
- source-trust and evidence-assurance labels;
- confidentiality class and data categories;
- secret-detection disposition;
- retention mode, scope, expiration, and hold status;
- access scope;
- evidence references.

### 4.5 Rank candidate cognitive actions

Candidate actions may include:

```text
retrieve_more
read_evidence
request_verification
open_or_resume_investigation
propose_observation
propose_claim
propose_mark_stale
propose_supersession
propose_consolidation
record_utility
prepare_rehydration
request_human_approval
stop
```

Each candidate records:

```text
expected_information_gain
expected_cost
expected_latency
expected_risk
reversibility
evidence_strength
policy_compatibility
dependency_availability
```

### 4.6 Select and propose

The Subagent selects one or a bounded batch of non-conflicting actions.

It must record:

- selected action;
- alternatives considered;
- why the selection dominates;
- applicable policy;
- expected outcome;
- whether approval is required.

It cannot commit canonical state.

### 4.7 Await outcome

Possible outcomes include:

```text
host_action_completed
host_action_failed
verification_supported
verification_contradicted
verification_inconclusive
governance_accepted
governance_rejected
needs_evidence
conflict_detected
policy_review_required
timeout
external_dependency_unavailable
```

The cycle does not infer success from absence of an error.

### 4.8 Attribute utility

Role owner:

- Outcome and utility recorder.

Utility dimensions include:

```text
useful
partially_useful
irrelevant
dead_end
misleading
harmful
```

Lifecycle or epistemic outcomes are recorded separately:

```text
item_outcome:
  unchanged
  corrected
  superseded
  retracted
  expired
```

Attribution must identify:

- item or reasoning path;
- task/domain scope;
- evidence for the utility judgment;
- confidence;
- whether the effect was immediate or delayed.

### 4.9 Update operational self-state

Role owner:

- Self-state maintainer.

The self-state contains measurable facts:

```text
current_goal
active_investigation
known_verified
known_uncertain
pending_verification
failed_paths
available_tools
budget_remaining
blocking_conditions
next_justified_action
```

Unsupported descriptions such as “I understand the system” are prohibited.

### 4.10 Continue, stop, or escalate

The cycle records one stopping decision.

## 5. Frozen stopping conditions

A cycle stops or escalates when:

```text
objective_satisfied
no_justified_action_remains
budget_exhausted
policy_refusal
human_approval_required
contradictory_evidence_unresolved
repeated_non_progress
external_dependency_unavailable
safety_or_privacy_boundary_reached
task_cancelled_or_superseded
```

Repeated non-progress requires a configurable threshold and must consider whether new evidence changed the state.

## 6. Policy executor boundary

The Memory policy executor:

- reads the active policy;
- plans within policy;
- predicts likely governance disposition;
- refuses proposals it can identify as invalid;
- records the applied policy version.

Ola Core:

- authoritatively evaluates policy;
- enforces transitions;
- commits or rejects transactions;
- emits governance receipts.

The Memory Subagent cannot redefine policy or treat its prediction as a receipt.

## 7. Verification coordinator boundary

The Memory Subagent decides:

- what requires verification;
- why verification matters;
- which method is suitable;
- what evidence is missing.

Ouroboros:

- creates the verification contract;
- structures the investigation;
- correlates results;
- interprets support, contradiction, or inconclusiveness.

The host agent or authorized adapter performs the action.

## 8. Utility-learning constraints

Utility may:

- change retrieval priority;
- change context-selection priority;
- change verification order;
- deprioritize repeated dead ends;
- influence rehydration selection;
- inform procedure recommendations.

Utility may not:

- promote epistemic state;
- erase contradictory evidence;
- bypass verification;
- permanently suppress exploration;
- override policy;
- convert task-local usefulness into universal truth.

Required anti-feedback controls include:

```text
exploration_quota
utility_decay
task_and_domain_scope
source_diversity
counterfactual_evaluation
rollbackable_policy_version
minimum_reconsideration_trigger
```

## 9. Rehydration cycle

The Rehydration planner selects:

```text
goal
completed_work
verified_claims
unresolved_questions
failed_paths
active_scope
evidence_references
repository_or_environment_version
next_action
next_action_rationale
policy_and_safety_constraints
```

Ola produces and verifies the durable packet.

Shared Runtime assembles and delivers it without changing labels.

## 10. Audit and evaluation

Every role must have role-specific fixtures.

Minimum metrics:

| Role | Metric |
|---|---|
| Retrieval planner | relevant evidence per retrieval cost |
| Context curator | useful context retained under budget |
| Gap detector | precision and actionability of gaps |
| Verification coordinator | uncertainty reduced per action |
| Write proposer | accepted useful writes versus rejected noise |
| Consolidation planner | compression without provenance loss |
| Contradiction manager | conflict-classification accuracy |
| Staleness monitor | stale use prevented versus false alarms |
| Utility recorder | predictive value of utility labels |
| Rehydration planner | recovery efficiency and duplicate work |
| Self-state maintainer | accuracy of operational state |
| Policy executor | correct planning compliance and refusals |

End-to-end success cannot hide role-level failure.

## 11. Failure and escalation

The Subagent must escalate when:

- required evidence is inaccessible;
- policy versions conflict;
- no authorized verification method exists;
- repeated cycles produce no information gain;
- context budget cannot preserve required safety or provenance;
- external action requires human authorization;
- governance receipts are unavailable or inconsistent.

Escalation is a valid outcome, not a planning failure.

## 12. Consequences

### Positive

- Converts twelve roles into a coherent executable protocol.
- Makes planning decisions auditable.
- Enables role-level evaluation and ablation.
- Prevents utility from becoming a hidden truth signal.
- Defines stopping and escalation explicitly.

### Negative

- Adds planning telemetry and storage.
- Requires budgeting and ranking models.
- May increase latency for small tasks.
- Requires careful privacy controls for cycle records.

## 13. Acceptance criteria

This annex is accepted when:

- the canonical cycle is approved;
- cycle-record fields are accepted;
- stopping conditions are frozen;
- policy and verification boundaries are accepted;
- utility-learning restrictions are adopted;
- M7 evaluation fixtures are assigned.

# ADR-0001-F: Minimum Trust, Privacy, and Retention Prerequisites

- **Parent decision:** ADR-0001
- **Status:** Proposed — frozen candidate for ratification
- **Decision scope:** Minimum controls required before evidence ingestion and claim-proposal integration
- **Prepared:** 2026-07-22

## 1. Context

ADR-0001 schedules advanced governance for M10. However, M5 begins admitting raw evidence into Ola and M6 permits Ouroboros conclusions to become claim proposals.

Minimum trust, privacy, retention, and contamination controls are prerequisites for those milestones. They cannot first appear after evidence and proposals are already flowing through the unified product.

## 2. Decision

Before M5 evidence integration, every admitted evidence item must have:

```text
source_class
source_trust
evidence_assurance
epistemic_state
confidentiality_class
data_categories[]
secret_detection_disposition
retention_mode
retention_scope
expires_at
hold_status
workspace_or_user_scope
access_decision
redaction_outcome
derived_item_dependency_reference_policy
```

Before M6 claim proposals, the product must also preserve minimum contamination and derivation lineage.

M10 extends these controls; it does not introduce their foundation.

## 3. Source class

Minimum `source_class` values:

```text
user_assertion
trusted_local_source
local_tool_result
external_first_party_source
external_third_party_source
untrusted_external_content
agent_generated_inference
agent_generated_summary
third_party_agent_claim
verified_test_result
human_approved_conclusion
system_policy
```

Source class records origin, not truth, trust, assurance, or epistemic state.

## 4. Orthogonal trust, assurance, and epistemic fields

### 4.1 Source trust

Minimum `source_trust` values:

```text
untrusted
unknown
bounded
trusted_source
policy_authoritative
```

### 4.2 Evidence assurance

Minimum `evidence_assurance` values:

```text
unverified
corroborated
independently_verified
human_approved
```

### 4.3 Epistemic state

Minimum `epistemic_state` values:

```text
observed
inferred
candidate
verified
contested
possibly_stale
stale
superseded
```

Trust cannot increase solely because content is repeated, summarized, embedded, retrieved frequently, or asserted by multiple agents sharing the same source.

Assurance and epistemic state must not be encoded as source trust. Independent verification must be distinguishable from correlated repetition.

## 5. Confidentiality, data category, and secret disposition

### 5.1 Confidentiality class

Minimum `confidentiality_class` values:

```text
public
internal
confidential
restricted
```

### 5.2 Data categories

`data_categories[]` may contain zero or more values such as:

```text
personal_data
highly_sensitive_personal_data
financial_data
health_data
source_code
legal_material
credential_material
```

### 5.3 Secret detection disposition

Minimum `secret_detection_disposition` values:

```text
none_detected
possible_secret
confirmed_secret
credential_or_token
policy_exempt
manual_review_required
```

Policy defines permitted storage, display, retrieval, sharing, and redaction for the combined classification.

## 6. Retention dimensions

### 6.1 Retention mode

Minimum `retention_mode` values:

```text
ephemeral
retain_until_expiry
retain_for_audit
do_not_retain
```

### 6.2 Retention scope

Minimum `retention_scope` values:

```text
task
session
project
workspace
user
organization
```

### 6.3 Hold status

Minimum `hold_status` values:

```text
none
policy_hold
legal_hold
security_hold
manual_review_hold
```

Each retained item records:

```text
retention_mode
retention_scope
created_at
expires_at
hold_status
retention_policy_version
deletion_or_review_trigger
```

These dimensions are independent. An item may be user-scoped and retained for audit, or project-scoped and retained only until expiry.

## 7. Workspace and user scope

Every retained item is bound to an access scope such as:

```text
workspace_id
project_id
user_id
organization_id
task_id
run_id
```

Cross-scope retrieval is refused unless an explicit policy authorizes it.

Scope must survive projections, summaries, and evidence references.

## 8. Evidence admission

Evidence admission follows:

```text
receive candidate evidence
→ identify source and scope
→ assign source trust and evidence assurance
→ classify confidentiality and data categories
→ run secret detection
→ apply redaction policy
→ decide retention mode, scope, expiry, and hold
→ compute canonical digest
→ store protected raw evidence or refuse
→ issue bounded evidence reference
```

Admission dispositions include:

```text
accepted
accepted_redacted
accepted_metadata_only
rejected_secret
rejected_scope
rejected_policy
do_not_retain
quarantined_for_review
```

A successful tool execution does not imply evidence-retention permission.

## 9. Redaction

Redaction must record:

```text
redaction_applied
redaction_policy_version
redacted_regions_count
original_digest
retained_digest
raw_original_retention
```

Where policy forbids retaining the original, the system must not keep it merely to support later debugging.

Derived summaries must remain linked to the redacted or source evidence according to policy.

## 10. Secret detection

Secret detection uses the orthogonal `secret_detection_disposition` taxonomy defined in §5.3.

Confirmed secrets are refused or stored only in a specifically authorized protected domain.

General logs, orientation packets, diagnostics, and reasoning artifacts must not contain secret values.

## 11. Minimum contamination lineage

Before M6, every proposal derived from evidence must record:

```text
source_evidence_refs
derivation_type
producer_agent
producer_version
verification_contract_ref
independent_verification_refs
shared_source_group
source_trust
evidence_assurance
epistemic_state
contamination_flags
```

A summary or inference cannot outrank its strongest supporting evidence.

Multiple claims derived from one source remain correlated and must not be counted as independent confirmation.

## 12. Derived-item dependencies

Derived claims, summaries, procedures, and projections must retain dependency references.

When raw evidence:

- expires;
- is deleted;
- is reclassified;
- is found corrupted;
- loses access authorization;

the system must identify affected derived items and apply policy:

```text
retain_with_provenance_gap
mark_needs_revalidation
mark_stale
restrict_access
rebuild_projection
delete_or_tombstone
manual_review
```

## 13. Access control

Access decisions must consider:

- actor;
- user/workspace scope;
- requested operation;
- confidentiality class and data categories;
- secret-detection disposition;
- retention mode, scope, expiry, and hold;
- policy version;
- purpose;
- target subsystem;
- whether raw or derived data is requested.

Access denial must not leak the protected content through diagnostics.

## 14. Orientation and context protections

Orientation assembly must preserve:

- source class and source trust;
- evidence assurance and epistemic state;
- confidentiality class and data categories;
- secret-detection disposition;
- retention mode, scope, expiration, and hold status;
- provenance;
- redaction state;
- access scope;
- staleness and safety labels.

Shared Runtime may omit protected content but must not silently downgrade its classification.

The Memory Subagent may select content only within the caller's authorized scope.

## 15. Logging and telemetry

Operational telemetry must use:

- identifiers;
- digests;
- bounded classifications;
- counts;
- reason codes.

It must not copy raw sensitive payloads into general logs.

Research telemetry must define:

- allowed fields;
- de-identification;
- retention;
- contamination controls;
- opt-in or policy basis.

## 16. Minimum forgetting behavior

Before advanced governed forgetting exists, the product must support:

- retention expiry;
- task/session cleanup;
- `do_not_retain`;
- access revocation;
- evidence-reference invalidation;
- affected-derived-item identification;
- audit of deletion or tombstoning.

M10 may add simulation, cascading policy, legal workflows, and user-facing impact previews.

## 17. High-assurance refusal

High-assurance workflows refuse when:

- source class is missing;
- confidentiality or data categories are unresolved;
- secret disposition is unresolved;
- retention mode, scope, expiry, or hold policy is unavailable;
- scope is ambiguous;
- evidence digest does not match;
- required raw evidence expired;
- derivation lineage is incomplete;
- independent verification is claimed but sources are correlated.

## 18. Consequences

### Positive

- Prevents unsafe evidence ingestion before advanced governance.
- Preserves contamination lineage.
- Makes scope and retention explicit.
- Supports later governed forgetting and impact analysis.
- Reduces sensitive-data leakage into reasoning and telemetry.

### Negative

- Adds admission latency and metadata.
- May reject evidence that current systems would store.
- Requires policy configuration before M5.
- Creates dependency handling when evidence expires or is deleted.

## 19. Acceptance criteria

This annex is accepted when:

- orthogonal source, trust, assurance, epistemic, confidentiality, data-category, secret, retention, scope, and hold taxonomies are approved;
- evidence-admission dispositions are frozen;
- scope and access semantics are assigned to M3/M4;
- contamination lineage is required before M6;
- derived-item dependency behavior is accepted;
- logging and orientation protections are incorporated into contract tests.
